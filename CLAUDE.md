# duohuygo-xiangqi

Duolingo-style web app for learning Chinese chess (Xiangqi): lessons and puzzles. Static site only: no backend in this phase.
Must work in desktop and phone browsers and as an installable, offline-capable PWA.

## Planning and automated workflow

- **[docs/PLAN.md](docs/PLAN.md)** lists the tasks (goal, acceptance criteria, status, notes). Tasks 1–3 are done.
- **Work directly on `main`**: no feature branches, no PRs (only the owner and Claude work on this repo, and
  there are no users yet). Commit and push to `main` once lint, build and tests pass; every push to `main`
  deploys to GitHub Pages.
- **[docs/DRIVER.md](docs/DRIVER.md)** is the exact procedure for "do the next task": `implementer` →
  `tester` → `reviewer` → fix loop (max 3 attempts) → update PLAN.md → commit and push to main → summary.
- Subagents live in `.claude/agents/` (`implementer`, `tester`, `reviewer`). CI (`.github/workflows/ci.yml`)
  runs `npm ci`, build and test on pull requests; on `main`, the deploy workflow runs the tests before publishing.
- Never change `src/engine` behavior. If you find an engine bug, stop and report it.

## Stack

Vite + React + TypeScript, Tailwind CSS v4 (via `@tailwindcss/vite`, no config file), Vitest,
vite-plugin-pwa (manifest + Workbox service worker, `registerType: 'autoUpdate'`), oxlint.
`base: './'` in `vite.config.ts` so the build can be served from any sub-path on static hosting.

## Lesson content

- Add or edit lessons in `src/content/lessons/NN-name.json`; every string field is an i18n key
  that must exist in `src/i18n/messages.ts` with both `en` and `vi` text.
- Exercise types: `learn`, `select-squares`, `move` (goals: `reach`, `any`, `check`, `checkmate`,
  `defend`), `capture`, `combination`. Answers are computed by the engine; `solution` fields are only
  verified, never trusted.
- `defend` (`goal.depth` 1–3, default 1): Black threatens mate in `depth`; any move that leaves Black
  without a forced mate in `depth` is correct. Depth 3 is judged after a short "Checking your move…" pause.
- `combination` (`src/lessons/combination.ts`): 2–4 moves of the learner's side (Red in all legacy content) against the engine's best defence,
  goal `checkmate` (exactly N moves, not fewer) or `win-material` (2–3 moves; ≥ 2 points by the same search
  as win-material puzzles, horizon = 2 plies per Red move). `solution` is the main line (Red, Black, …, Red);
  any Red move the engine confirms is accepted. Optional `hints` (one i18n key per Red move).
  Only the played move is searched (`isWinningMove`). Black's reply: fewest winning answers when 1–2 Red
  moves remain, "longest resistance" (no shorter mate) when 3+ remain. Mates in 4 must list every winning
  first move in `firstMoves` (computed at authoring time: a full list takes the engine seconds to minutes);
  the quick validator plays the main line, `npm run content:deep` proves the list wins and is complete.
  Run it after changing any mate-in-4 exercise. Moves in a mate in 4 are judged after a short pause.
- Positions use `pieces` maps (`{ "e0": "K", "d9": "k" }`) or `fen`. Exercises are played by their `side`
  (default `red`): the side to move must equal `side`, and `square`/`from` must hold a piece of that side.
  The judges (`src/lessons/answers.ts`, `combination.ts`) take the mover from the position (`start.turn`), so a
  Black exercise is judged exactly like its colour-swapped Red twin (`src/lessons/mirror.test.ts`).
- Schema v2 (`src/content/types.ts`, curriculum-upgrade design 02 §3.3, 07 §2.1/§5.1). **Legacy units** (ids
  `u1`–`u15`) keep every new field optional. **New-course units** (id = level prefix `b i a e m` + 2 digits, e.g.
  `b05`; `track` required and matching the prefix; lessons `b05l2`) need on every exercise `id` (`b05l2-04`;
  pool items `b05-p03`), `version` (≥ 1), `status` (`draft` · `verified` · `reviewed` · `published` · `retired`),
  `source` (`kind`: `generated` + `generator`/`seed`, `authored`, `derived` + `derivedFrom`/`transform`,
  `course-game` + `gameId`/`moveNumber`, `legacy` + `legacyRef` like `u7l1#2` or `m2-07`; optional `refs`
  citations) and an explicit `side`; practice items (not `learn` cards) also need `strand` (`RS TC OD PA DE PP`),
  `nature` (`tactic` | `quiet`), `critical` and `misconceptions` (ids like `b06.m2`, may be empty). Ids are unique
  and new-course ids must not be in `src/content/retired-ids.json` (append ids there when they retire).
- Legality (`src/content/legality.ts`, also used by the puzzle verifier): at most the starting number of each
  piece, and only reachable points (General/Advisor in the palace, Elephant on its 7 points, a Soldier before its
  river only on files a, c, e, g, i, and at most one own Soldier per file before it crosses). Errors for new-course
  positions; for legacy positions they are only reported (`validateContent(...).notices`, `legacyPlacementNotices`):
  today the 13 `POS` positions (12 unreachable Soldiers + `u13l2#4`, two unpromoted Black Soldiers on file a).
- A unit may have an extra-practice `pool` (array of practice exercises, no `learn` cards), validated exactly
  like lesson items. `src/content/normalize.ts` (`normalKey`, `duplicateGroups`) compares positions up to file
  mirror and colour swap; today the only duplicates are 7 learn cards showing the next item's position.
- Release path (curriculum-upgrade 07 §6, 05 §8.4.1): units load in track-rank order, then file name, so each track
  is one block. `CURRENT_RELEASE` in `src/content/release.ts` names the release state; `src/content/release.test.ts`
  proves the content and `LEGACY_MAP` match it and no other state (T1). A release item changes the state, the content
  and the map together. New-course items are served only when `published` (`reviewed` in the course preview) with an
  approving record in `src/content/reviews/<unitId>.json` bound to id + version + contentHash (normalised item JSON
  without `status` + en/vi texts; `npx tsx scripts/review-hash.ts <unit>`); the reviewer must differ from the author,
  no e-mail addresses. Legacy lessons are exempt only while live in the state. Unreviewed material goes in
  `src/content/drafts/` (never loaded). The loader does not filter by status; the release test fails the build instead.
  Items in a published level must be `published`; items of a level not yet published are at most `reviewed` (this is
  how T1 tells REL-4 from REL-5). A record approves only if its latest `content-reviewer` verdict is `approve`; record
  ids must belong to the file's unit (`<unit>l…`, `<unit>-p…`, `-c…`, `-g…`). Slow content-verifier tests carry an
  explicit 120 s timeout (they take 20–45 s on a loaded machine).
- Course preview: `VITE_COURSE_PREVIEW=1 npm run build` (or `npm run dev`) shows the new-course path instead of the
  legacy path: published levels plus the fully reviewed units of unpublished levels, by level, first lesson of each
  level open. Never set it for the deployed build (a test checks the workflows). New-course completion is stored in
  the learning records (`via: lesson`, or `placement` for a passed jump test; `contentVersion` = highest item
  `version` in the lesson), never in the v1 list.
- `npx vitest run src/content` validates all content and plays every exercise through the engine.
- Units have a `track`, in order: `basics` (files 01–04: 4 short units, 9 lessons, the default),
  `intermediate` (files 07–10, ids u7–u10: cannon mates, horse/chariot mates, tactics, combinations),
  `advanced` (11–12: discovered check, decoys, stopping mate in 2, mate in 3), `expert` (13–14: only-move
  defence, quiet moves on a full board, discovered attack in 3, mate in 4) and `master` (15: quiet mates in
  4, full-board mates in 4, and a challenge mixing a mate-in-3 defence with mates in 4). Each track unlocks
  in order on its own, and the first lesson of every track is open from the start
  (`src/lessons/progress.ts`). Home shows a header per track and a "jump to <level>" banner
  (`jumpBannerTrack`): it points to the lowest higher level not started yet and disappears once the learner
  completes a lesson there or in a higher level. A new track needs `track.<id>.jumpTitle`/`jumpBody` text. Progress
  is stored via `src/storage` (localStorage today). Text keys follow the lesson id (`u2l1.e3`, `u2l1.x3`).
- Jump ahead (Duolingo-style): tapping a locked lesson, or "Jump here" on a locked unit, opens a dialog
  and then a test (`jumpTest` in `src/lessons/progress.ts`): the last two practice exercises of every
  skipped lesson, at most `JUMP_TEST_MAX` (8), played in `LessonPlayer` with `test` = `JUMP_TEST_LIVES` (3)
  lives of its own (real hearts untouched, works at 0 hearts). Passing marks the skipped lessons complete
  with no XP; running out of lives ends the test and changes nothing.
- Home scroll position (`focusLessonId` on `Home`, centred, once per appearance, not on tab switches): when
  the app opens, the furthest lesson reached (`furthestLesson`: in the highest track with a completed lesson,
  the first one not completed, or its last lesson; derived from progress, so the same on every device, and
  none for a new learner); after a lesson or jump test is finished or quit, that lesson.
- Intermediate positions are original: random positions kept only when the solver proves the pattern
  (unique forced mate, best defence, clean fork). Do not copy positions from books or websites.
- After adding a new lesson JSON file, clear Vitest's cache (`rm -rf node_modules/.vitest-cache`) if the
  tests do not see it: the cached transform of `import.meta.glob` can be stale.

## Puzzles

- Every puzzle is original: random plausible positions from `scripts/generate-puzzles.ts` (seeded,
  deterministic), kept only when the solver proves a unique solution. Do not copy puzzles from
  books, websites or databases.
- `src/content/validate-puzzles.ts` is the verifier: legal position (piece counts, reachable points,
  opponent not in check), stored line legal, goal reached, and the first move is the ONLY winning
  move (plus any listed `alternatives`). For mate-in-2 every defence is searched; the stored
  reply must be a best defence (fewest mating answers). `npx vitest run src/content` runs it.
- Win-material uses `searchScore`/`moveScore` (4 plies + capture quiescence, beginner piece values);
  "winning" means gaining at least 2 points (`WIN_MATERIAL_THRESHOLD` in `src/puzzles/logic.ts`).
- In the player, later moves are accepted whenever the engine confirms they still win, not only the
  stored move. Solved puzzle ids are stored through `src/storage` (`createPuzzleProgressRepository`).
- All puzzles are currently Red to move (drawn with Red at the bottom).

## Playing Black and notation (curriculum upgrade)

- `Board` takes `orientation` (`'red'` default | `'black'`: turned 180°, a point is drawn at x = 8 − file,
  y = rank; river labels swapped; board name "…, Black at the bottom") and `fileNumbers` (opt-in: each side's
  numbers 1–9 along its own edge, counted from that side's right). Taps and accessible names stay on ICCS squares.
  The players do not pass these props yet; legacy boards are unchanged.
- Learners read traditional notation; ICCS stays internal. `formatMove(move, positionBefore, 'traditional' |
  'iccs', lang)` in `src/notation/format.ts`; names, letters, symbols and front/rear markers are in
  `docs/curriculum-upgrade/glossary.md` (the source; change both together).
- Generic feedback text is colour-neutral ("your opponent" / "đối phương") or uses `{side}` (`side.toMove`).
  Legacy keys that still say "Black" have `.neutral` twins for players showing a Black exercise.
- `npm run ui:check` also builds `scripts/ui-fixtures/black.html` (Black at the bottom, file numbers, a move shown
  in notation) into `ui-check-output/fixture-dist/` and checks it at the same viewport, served on port 4198.

## Learning records (curriculum upgrade)

- New-course progress is stored through `createLearningRepository` under `learning.records.v1` (completed /
  mastered / applied with provenance, plus the exposed item set; additive changes only, unknown fields and a higher
  `schema` are preserved) and `learning.attempts.v1` (attempt log, local only, newest 2,000). A stored value that is
  not a JSON object reads as empty and is copied to `learning.records.v1.backup` on the next write.
- New-course ids are never written to `progress.completedLessons.v1`. Legacy completion is derived at read time
  (`completedView` in `src/progress/legacy.ts`) and never stored; loading writes nothing. Each release that retires
  legacy lessons adds their `LEGACY_MAP` entries and bumps `LEGACY_MAP_VERSION` (corrections only add targets).
- Reset progress clears the v1 completed list, the records and the attempt log; puzzles, settings and gamification
  are untouched. Design: `docs/curriculum-upgrade/design/05-migration.md` §8.

## XP, hearts, daily goal and streak

- Rules live in `src/gamification/rules.ts` (documented at the top of the file); the clock is injected
  (`App` takes an optional `now: () => Date`, tests pass a fixed one). Days are the device's local date.
- XP: lesson first completion 10, replay 5, first puzzle solve 5 (no difficulty bonus), reveal/re-solve 0.
- Hearts: max 5, −1 per wrong lesson answer, +1 every 30 min computed from timestamps. At 0 hearts no
  lesson can be started (the current lesson can still be finished); puzzles never cost hearts.
- Daily goal 10/20/30/50 XP (default 20), met when today's XP ≥ goal; the streak counts consecutive met days.
- A clock that goes backwards never grants hearts and never breaks or extends a streak.
- State is stored as one JSON value under `gamification.state.v1` via `createGamificationRepository`.

## Sound, animation and phone layout

- Sound effects (`correct`, `wrong`, `move`, `capture`, `complete`) are synthesized with Web Audio in
  `src/sound/player.ts`: no audio assets, so no licences. Components call `useSound().play(effect)`.
- The AudioContext is created/resumed only in `unlock()`, run from pointerdown/keydown listeners
  (autoplay policy). When muted (`settings.muted.v1` via `createSettingsRepository`), `unlock()` does
  nothing, so a stored mute means no audio at all. Without Web Audio (Node/jsdom) it is a silent no-op.
  `App` takes an optional `audio` factory; tests inject `createFakeAudio()` from `src/sound/fake-audio.ts`.
- Animations are CSS classes in `src/index.css` (`piece-slide`, `piece-captured`, `feedback-in`,
  `feedback-pop`, `feedback-shake`, `celebrate-pop`, `confetti-piece`, `heart-lost`). Every one must be
  switched off in the `prefers-reduced-motion` block, and Tailwind `animate-*` must be `motion-safe:`
  (`src/motion.test.ts` enforces both).
- Fixed footers: the players measure the footer (`useElementHeight`) and render a spacer of that height
  after the board, and `.board-fit` caps the board so it fits above the footer on short screens. Do not
  go back to fixed `pb-*` guesses. Fixed bars add safe-area insets (`.safe-px`, `env(safe-area-inset-*)`).
- `npm run ui:check` fails on horizontal scroll, controls under 44px or clipped at the edge, and a fixed
  bar covering the board's last row. Run it at 320, 360, 414 wide and in landscape (`--width 740 --height 360`).

## Account login and sync (optional)

- Off unless BOTH `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` are set at build time. Without them
  there is no account UI and the build contains no Supabase code (the `import.meta.env` check in
  `main.tsx` is folded away). With them, `@supabase/supabase-js` is a separate lazy chunk.
- The app works unchanged when signed out. Local data (src/storage) is always the source of truth for
  the UI: `App` reads/writes through `account.store`, a wrapper that schedules a sync 2 s after a
  meaningful local change. A sync pulls the account row, merges, writes the merge locally (then the UI
  re-reads via `onDataChanged`) and pushes it. It also runs on sign-in / app start with a session and
  when the device comes back online. Errors never reach gameplay; they only show as a sync status.
- Components get an `AccountService` (`App`'s optional `account` prop) and never import Supabase.
  Tests use `createFakeBackend()` from `src/sync/fake-backend.ts` or a fake Supabase client: no network.
- **Merge rule** (`src/sync/merge.ts`): completed lessons / solved puzzles = union; XP = per-day max,
  total = max of the XP older than the per-day history + sum of merged days (never below either total);
  streak = the side with the later `lastGoalDay` (same day: longer streak), best streak = max;
  hearts = refill both by time, then the side with FEWER hearts (sync never grants hearts);
  language, sound and daily goal = this device's value, the account's only fills in missing ones.
  Corrupt or missing remote fields are ignored. Idempotent; commutative except the preferences.
  Union cannot express deletion: "Reset progress" while signed in is undone by the next sync.
- **Learning records (`data_v2`).** The whole `learning.records.v1` value syncs in a separate column,
  `progress.data_v2` (migration `supabase/migrations/20261023000000_progress_data_v2.sql`); the attempt log stays
  local. `data` keeps the v1 `RemoteData` shape for older builds, which read and upsert only `{ user_id, data }` and
  so should leave `data_v2` untouched (confirmed only by T15 below). Pull = `select('data, data_v2')`, push =
  `{ user_id, data, data_v2 }`. Merge (`src/sync/merge-records.ts`): completed = union, same id → earlier `at`, then
  `lesson` before `placement`, then JSON order (`betterCompletion`, also used locally by `grantCompletion`);
  mastered / applied = higher score, then later `at`, then JSON order (never lowered); exposed = union; schema = max;
  unknown top-level fields = local value, else remote; corrupt remote data ignored field by field. Both fingerprint
  uses (scheduled-sync skip and push skip) include the records; a null or corrupt remote `data_v2` is overwritten.
  New enum values in a grant (e.g. a new `via`) are a **breaking** change: older new-format builds drop entries they
  do not recognise and would push them away — use a new key/column instead (05 §8.9 additive-only rule).
- **Missing `data_v2` column** (migration not run): pull falls back to `select('data')`, push to `{ user_id, data }`
  (PostgreSQL `42703` / PostgREST `PGRST204`, remembered until the next app start, so a stale schema cache right
  after the migration shows a sync error until restart). v1 data still syncs, records stay on the device, status
  shows `error`.
- **Owner action before any deploy that writes `data_v2`:** run the new migration on the real project, then pass
  T15 steps 3–5. The automated tests use a fake backend; T15 is the only check against real PostgREST
  (curriculum-upgrade 04 R5 / 05 MU2).

**T15 (manual; real Supabase project or `supabase start`)**

1. Apply `supabase/migrations/*.sql` in order. Check that `select column_name, is_nullable, column_default from

3. **Update keeps `data_v2`:** run the previous build (e.g. `git worktree add ../xq-old <commit before S2.11>` and
   `npm run dev` there; it uses supabase-js single-object upsert with `onConflict: 'user_id'`), sign in as A and

4. **Insert gives null:** with the previous build, sign in as a new user B and sync once: B's row has `data_v2`
   null. Then sign in as B with the new build: `data_v2` is filled in.
5. **RLS on both columns** with B's access token and the anon key (curl `/rest/v1/progress`): selecting A's row

## Engine conventions

- Square index = `rank * 9 + file`. Files `a..i` left to right from Red's side; ranks `0..9` with
  rank 0 = Red's back rank. Square names are ICCS style: Red general starts on `e0`, Black on `e9`.
- FEN lists rank 9 first. Uppercase = Red. Letters `k a b n r c p` (`e`/`h` accepted as aliases).
  Side to move `w` (or `r`) = Red, `b` = Black.
- Positions are immutable from the outside: `makeMove` returns a new `Position`.
- The flying-general rule is handled inside `isGeneralAttacked` (the enemy general "attacks" along an open file).
- Stalemate is a loss for the side to move (`gameStatus` returns `{ kind: 'stalemate', winner }`).
- Not implemented yet: perpetual check/chase rules, repetition, move-count draws.
- Perft from the start position must equal 44 / 1,920 / 79,666 / 3,290,240 (depths 1–4).
